# UIAuto 顶层设计：平台化用例管理与执行

> 版本：v0.2 · 2026-03-08  
> 状态：草案，供评审与迭代

---

## 1. 背景与目标

UIAuto 从早期的「从 GitHub 拉取用例 → 组计划 → 执行」MVP，已演进为支持**浏览器录制、用例仓库、环境管理、试跑、定时任务、协作通知**的测试平台。

未来用例进入平台的方式有三条**并列的生产面**，均由本平台直接支持：

| 生产面 | 使用者 | 说明 |
|--------|--------|------|
| **① 录制回放** | 测试人员（本平台） | 浏览器插件 + 工作台录制操作，生成 Playwright 脚本并保存 |
| **② 手动导入** | 其他测试人员（本平台） | 在用例库粘贴脚本、上传文件、在线编辑后入库 |
| **③ MCP 调用** | 外部 Agent / 集成方 | 通过 MCP 进行用例导入、修改、建计划、执行、查报告等全链路操作 |

大模型生成用例是 MCP 生产面的典型场景（Agent 生成脚本后调用 `import_case`），但**不单独作为第四条生产通道**——它与其他自动化集成一样，统一走 MCP。

无论经哪条生产面进入，平台的核心职责是统一的：

> **承接 → 管理 → 执行 → 报告**

因此本设计明确：**完全移除 Git 仓库作为用例存储与同步的方式**，平台自身为用例与环境的唯一控制面（Control Plane）。

## 2. 平台定位

```
                         ┌── 生产面 ─────────────────────────────────────┐
                         │                                             │
              ┌──────────┴──────────┐   ┌──────────────┐   ┌──────────┴─────────┐
              │ ① 录制回放           │   │ ② 手动导入    │   │ ③ MCP 对外服务      │
              │ 插件 + 录制工作台     │   │ 用例库 UI     │   │ Agent / 脚本 / IDE  │
              └──────────┬──────────┘   └──────┬───────┘   └──────────┬─────────┘
                         │                     │                      │
                         └─────────────────────┼──────────────────────┘
                                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                          UIAuto 控制面（消费面亦在此）                         │
│   用例库 · 环境 · 计划 · 调度 · 执行 · 报告 · 权限                            │
└─────────────────────────────────────────────────────────────────────────────┘
                         ▲                              ▲
                         │                              │
                  平台 Web 前端                    REST API（内部）
                  管理 / 执行 / 查看报告            录制器 / 前端共用
```

**三条生产面能力对照：**

| 能力 | ① 录制回放 | ② 手动导入 | ③ MCP |
|------|-----------|-----------|-------|
| 创建用例 | ✅ 录制保存 | ✅ 粘贴/上传 | ✅ `import_case` |
| 修改用例 | ✅ 步骤编辑/脚本编辑 | ✅ 在线编辑器 | ✅ `update_case` |
| 管理环境 | ✅ 环境页 | ✅ 环境页 | ✅ `list/create/update_environment` |
| 建测试计划 | ✅ 计划页 | ✅ 计划页 | ✅ `create_plan` / `update_plan` |
| 执行测试 | ✅ 试跑/执行计划 | ✅ 试跑/执行计划 | ✅ `run_case` / `run_plan` |
| 查看报告 | ✅ 报告页 | ✅ 报告页 | ✅ `get_case_run` / `get_plan_run` |

三条生产面汇入**同一套 Service 层**，数据模型与执行引擎完全一致，避免「录制用例」与「导入用例」两套逻辑。

**UIAuto 不做：**

- 用例的 Git 版本管理（交给平台内版本表）
- 用例仓库的 clone / pull / 分支切换
- 与 GitLab/GitHub 权限体系绑定

**UIAuto 要做：**

- **生产面**：录制回放、手动导入、MCP 对外服务（三条并列，本平台直接支持）
- **控制面**：用例资产的 CRUD、版本、标签、检索
- 执行环境（URL、账号、SwitchHosts、Headers）管理
- 计划编排与定时/Webhook 触发
- 单用例试跑与批量执行
- 执行报告（日志、截图、录屏、trace）

## 2.1 生产面详细设计

### ① 录制回放（平台内置）

**入口：** 录制工作台（`CaseRecord`）、浏览器扩展

**流程：**

```
安装扩展 → 连接录制会话 → 浏览器内操作 → 生成 steps + script
    → 可选采集 storageState → 保存到用例库（source=recorded）
    → 可立即试跑验证
```

**平台提供：**

- 步骤列表编辑、断言/等待插入
- 脚本预览与手工微调
- 登录态 sidecar 自动附带
- 保存后进入统一用例库，与导入/MCP 用例无差别

### ② 手动导入（平台内置）

**入口：** 用例库「导入用例」、用例详情「新建」

**面向：** 不会/不想用录制的测试人员，或已有 Playwright 脚本的同事

**支持方式：**

| 方式 | 说明 |
|------|------|
| 粘贴脚本 | 文本框粘贴完整 `.spec.ts` / `.spec.js` |
| 上传文件 | 单文件或 ZIP（含 spec + 可选 auth.json） |
| 在线新建 | 空白模板起步，在平台内编辑 |

**流程：**

```
填写名称/描述/标签 → 提供脚本（+ 可选登录态）→ 选择默认环境
    → 校验（语法检查）→ 入库（source=imported 或 manual）
    → 可试跑、可加入计划
```

### ③ MCP 对外服务

**入口：** 独立 MCP Server，供 Cursor、内部 Agent 平台、CI 脚本等挂载

**定位：** 与平台 UI **能力对等**的编程接口——外部调用方无需登录 Web，即可完成用例全生命周期管理。

**典型调用方：**

- 大模型 Agent（生成脚本 → 导入 → 试跑 → 反馈修订）
- 测试同学的本地 IDE 助手
- 其他系统的自动化编排（如流水线触发回归计划）

**原则：**

- MCP Tool 与 REST API 一一映射，共用 `CaseService` / `PlanService` / `RunService`
- 鉴权独立（API Token + scope），操作审计记录 `created_by=agent:{name}`
- MCP 不绕过平台权限与执行队列

## 3. 设计原则

1. **单一用例模型**  
   录制、导入、LLM 生成最终落成同一种 `Case` 结构，执行引擎只认一种路径。

2. **Case Bundle，环境可选**  
   - 用例可**自带环境**（绑定包）：`default_environment_id` 或 `environment_snapshot_json` + `case.auth.json`  
   - 用例也可**不带环境**（通用用例）：`portability=portable`，执行时由计划或试跑指定环境  
   - 环境库：创建用例/计划时的可选模板  
   - **解析规则**：用例有环境 → 用用例的；用例无环境 → 用计划的（见 §6.7.4）

3. **平台托管优先**  
   脚本落盘在平台 workspace，元数据在 SQLite，不依赖外部仓库。

4. **API 与 MCP 共用 Service 层**  
   REST 给前端与脚本，MCP 给 Agent；业务逻辑不重复实现。

5. **渐进替换，接口向前兼容一段时间**  
   数据库与 API 可保留过渡期字段，但新产品能力不再围绕 Git 设计。

### 5.1 Cases Workspace

统一文件根目录（由原 `data/recorded-cases/` 演进）：

```
backend/data/cases/
├── _workspace/              # Playwright 项目壳（package.json、playwright.config.ts）
└── {user_id}/
    └── {case_id}/
        ├── case.spec.ts     # 当前版本脚本
```

## 6. 领域模型

### 6.1 Case（用例）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 主键 |
| `user_id` | int | 归属用户 |
| `name` | string | 显示名 |
| `description` | string? | 描述 |
| `tags` | string[] | 标签，JSON 存储 |
| `priority` | enum? | P0 / P1 / P2 |
| `source` | enum | `recorded` · `imported` · `manual` · `mcp` |
| `script_path` | string | workspace 内相对路径 |
| `default_environment_id` | int? | 用例自带环境（有则执行时优先使用） |
| `environment_snapshot_json` | object? | 用例自带环境快照（与上二选一或并存） |
| `has_auth` | bool | 是否有绑定的 `case.auth.json` |
| `metadata` | object | steps、生成 prompt、模型名等扩展信息 |
| `current_version` | int | 当前生效版本号 |
| `status` | enum | `active` · `archived` |
| `portability` | enum | `bundle`（默认，环境+登录绑定包）· `portable`（少数，可换环境） |
| `created_at` / `updated_at` | datetime | |

**约束：**

- 脚本格式统一为 **Playwright Test**（`@playwright/test`）
- 暂不支持多套 runner DSL；若未来需要 steps JSON，在入库前 compile 为 spec

### 6.2 CaseVersion（用例版本）

支持 LLM 多轮修订与人工编辑留痕。

| 字段 | 说明 |
|------|------|
| `case_id` | 所属用例 |
| `version` | 递增版本号 |
| `script` | 该版本脚本全文（或 script_path 快照） |
| `change_note` | 修订说明 |
| `source` | `user` · `llm` · `import` |
| `created_by` | user_id 或 `agent:{name}` |
| `created_at` | |

回滚 = 将 `current_version` 指向历史版本并写回 workspace 文件。

### 6.3 Environment（执行环境）

沿用现有 `execution_environments`，作为一等模型，不嵌入用例。

| 字段 | 说明 |
|------|------|
| `name` | 环境名 |
| `env_kind` | `test` · `staging` · `private` |
| `base_url` | 被测系统入口 |
| `test_username` / `test_password` | 账号登录 |
| `wps_company_name` | WPS 企业登录 |
| `switchhosts_text` | Hosts 映射 |
| `headers_json` | 额外请求头 |
| `extra_env_json` | 注入 Playwright 进程的自定义 env |

执行时合并规则（保持现有 executor 行为）：

```
最终 env = 系统默认 + Environment 字段展开 + 用例级 override（如有）
```

### 6.4 Plan（测试计划）

| 字段 | 说明 |
|------|------|
| `name` | 计划名 |
| `case_ids` | 用例 ID 列表（JSON 数组） |
| `environment_id` | **计划统一环境**：为组内「无自带环境」的通用用例提供执行上下文 |
| `schedule_cron` / `schedule_enabled` | 定时 |
| `run_browsers_json` | 浏览器矩阵 |
| `notify_*` | 协作群通知 |

建计划时**可指定统一环境**。执行时与用例自带环境按 §6.7.4 规则合并，**用例有环境则用用例的，没有用计划的**。

### 6.5 Run（执行记录）

| 类型 | 表 | 说明 |
|------|-----|------|
| 计划运行 | `runs` + `run_cases` | 批量执行 |
| 单用例试跑 | `case_runs`（由原 `recorded_runs` 重命名） | 编辑页/ MCP 触发 |

`run_cases` 关联 `case_id` + `case_version`，不再存 Git 路径。

### 6.6 手动导入包（Import Package）

手动导入的最小交付单元是 **「一个脚本 + 该脚本对应的执行上下文」**，而不是只有脚本文本。  
执行上下文再拆成两层（与录制保存逻辑对齐）：

```
Import Package
├── script          必填 · 单条 Playwright spec
├── environment     必填其一 · 被测地址 / Hosts / 账号等「怎么连上去」
└── auth            可选 · Cookie / storageState「已经登录的状态」
```

#### 6.6.1 三层职责（必须分清）

| 层 | 职责 | 典型内容 | 存储位置 |
|----|------|----------|----------|
| **Script** | 测什么、怎么点 | `test('...', async ({ page }) => { ... })` | `case.spec.ts` + `case_versions.script` |
| **Environment** | 在哪跑、用什么入口 | `base_url`、`switchhosts`、账号密码、headers | `execution_environments` 表，或用例级快照 |
| **Auth** | 免登录或已登录态 | `wps_sid` 等 Cookie、`origins` localStorage | `case.auth.json` sidecar（**跟用例绑定**） |

说明：

- **Environment ≠ Auth**：环境是「连哪个地址、用什么账号去登录」；Auth 是「导入时已经导出好的 Cookie 快照」，执行时可直接 `storageState` 注入，无需再调登录 API。
- 录制用例通常 Script + Auth 一起产生；手动导入时测试同学往往从本机带来 `*.spec.ts` + `*.auth.json` + 一段环境说明，平台应完整承接。
- Cookie **不写入** `cases.metadata_json`（避免 DB 膨胀），落盘到 `case.auth.json`，DB 只记 `has_auth`、cookie 数量等摘要。

#### 6.6.2 环境导入的两种模式

> **长期存储策略见 §6.7**：用例默认以绑定包入库（脚本+环境+登录）；下列模式描述**导入时**如何携带环境信息。

| 模式 | 字段 | 行为 | 适用场景 |
|------|------|------|----------|
| **引用已有环境**（推荐） | `environment_id` | 仅设 `default_environment_id` 为提示，执行时可覆盖 | 团队共用测试/预发环境 |
| **随包创建环境** | `environment.mode: "create"` | 导入时新建全局环境记录，供多用例复用 | 首次接入新环境 |
| **随包快照（例外）** | `environment.mode: "snapshot"` | 写入 `environment_snapshot_json`，仅绑本用例 | 临时/个人配置，**非默认路径** |

三者互斥优先级：`environment_id` > `environment.mode=create` > `environment.mode=snapshot`。  
导入时若未指定环境，可仅入库脚本，执行时再选环境（见 §6.7）。

#### 6.6.3 Import Package 数据结构（API / MCP 统一）

```typescript
/** POST /cases/import 请求体 */
interface CaseImportRequest {
  // ── 用例本体（必填）──
  name: string;
  description?: string;
  tags?: string[];
  priority?: 'P0' | 'P1' | 'P2';
  script: string;                    // Playwright spec 全文
  script_filename?: string;          // 默认 "case.spec.ts"

  // ── 执行环境（必填其一）──
  environment_id?: number;           // 引用已有环境
  environment?: ImportEnvironment; // 内联：新建或快照

  // ── 登录态（可选，建议与脚本成对导入）──
  auth?: ImportAuth;
}

interface ImportEnvironment {
  mode: 'create' | 'snapshot';
  name?: string;                     // create 时建议填
  env_kind?: 'test' | 'staging' | 'private';
  base_url?: string;
  headers?: { name: string; value: string }[];
  switchhosts_text?: string;
  test_username?: string;
  test_password?: string;
  wps_company_name?: string;
  extra_env?: Record<string, string>; // 注入 Playwright 进程的自定义变量
}

/** Playwright storageState 标准格式 */
interface ImportAuth {
  storage_state: {
    cookies: Array<{
      name: string;
      value: string;
      domain: string;
      path?: string;
      expires?: number;
      httpOnly?: boolean;
      secure?: boolean;
      sameSite?: 'Strict' | 'Lax' | 'None';
    }>;
    origins?: Array<{
      origin: string;
      localStorage?: { name: string; value: string }[];
    }>;
  };
}
```

校验规则（导入前 / `POST /cases/validate`）：

1. `script` 非空，且能被识别为 Playwright Test 结构
2. ~~`environment_id` 与 `environment` 不可同时为空~~ → **v0.2：环境可选**；无环境时 `portability=portable`，执行时由计划或试跑指定
3. 若提供 `auth.storage_state`，须符合 Playwright 格式；平台可过滤仅保留核心 Cookie（如 `wps_sid`）
4. `environment.mode=create` 时 `name` 必填（`base_url` 建议填）

#### 6.6.4 文件落盘（导入后）

```
backend/data/cases/{user_id}/{case_id}/
├── case.spec.ts           # script
├── case.auth.json         # auth.storage_state（有则写）
└── env.snapshot.json      # environment.mode=snapshot 时写入（可选）
```

数据库：

| 字段 | 来源 |
|------|------|
| `cases.script_path` | `case.spec.ts` 相对路径 |
| `cases.default_environment_id` | `environment_id` 或 create 后新环境 id |
| `cases.environment_snapshot_json` | snapshot 模式下的内联环境 |
| `cases.has_auth` | 是否写了 `case.auth.json` |
| `cases.source` | 固定 `imported` |

#### 6.6.5 文件上传（ZIP 包）

除 JSON API 外，手动导入支持 **标准 ZIP 包**，便于测试同学从本机打包：

```
my-case.zip
├── case.spec.ts              # 或任意 *.spec.ts（取第一个）
├── case.auth.json            # 可选，Playwright storageState
└── environment.json          # 可选，对应 ImportEnvironment（无则导入页选手动选环境）
```

`environment.json` 示例：

```json
{
  "mode": "snapshot",
  "name": "张三本地-文档测试",
  "env_kind": "test",
  "base_url": "https://www.kdocs.cn",
  "switchhosts_text": "10.0.0.1 www.kdocs.cn"
}
```

上传后服务端解压 → 解析三件套 → 走同一套 `ImportService.import()`，与 JSON API 逻辑一致。

#### 6.6.6 执行时环境解析（与 §6.7.4 一致）

```
对每条用例 resolved_environment =
  if 用例有 default_environment_id 或 environment_snapshot_json
    → 用用例自带环境
  else if 当前在计划内执行 且 计划有 environment_id
    → 用计划统一环境
  else if 试跑/执行请求显式传入 environment_id
    → 用传入环境
  else
    → 报错：缺少执行环境
```

登录态解析：

```
resolved_auth =
  if 用例有 case.auth.json → 优先使用
  else → 用 resolved_environment 的账号自动登录
```

#### 6.6.7 与录制保存的对齐

| 字段 | 录制（①） | 手动导入（②） |
|------|-----------|---------------|
| script | 录制器生成 | 用户粘贴/上传 |
| auth | 扩展采集 storageState | 上传 `case.auth.json` 或 JSON 字段 |
| environment | 试跑时选择 / 默认环境 | `environment_id` 或内联 `environment` |
| source | `recorded` | `imported` |

入库后二者在 `cases` 表中结构完全一致，执行引擎无差别对待。

### 6.7 用例模型：绑定包 + 通用用例并存

**结论：同时支持两类用例，执行时自动选择环境来源。**

| 类型 | `portability` | 环境 | 典型场景 |
|------|---------------|------|----------|
| **绑定包** | `bundle`（默认） | 自带环境 + 可选 auth | 私有化、特定账号录制、业务验收 |
| **通用用例** | `portable` | **无**环境信息 | 脚本可复用，由计划统一指定环境 |

两类用例在同一用例库、同一执行引擎中并存，**不拆表**。

#### 6.7.1 绑定包（多数业务场景）

```
Case Bundle
├── script
├── environment     ← 自带（id 或 snapshot）
└── auth（可选）    ← case.auth.json
```

录制、导入时带上环境与 Cookie，保存后即为绑定包。

#### 6.7.2 通用用例（少数，但明确支持）

```
Portable Case
├── script          ← 仅脚本，无环境字段
└── auth（通常无）
```

- 创建时不写 `default_environment_id` / `environment_snapshot_json`
- 加入测试计划时，**依赖计划的 `environment_id`**
- 脚本内建议使用 `process.env.BASE_URL`（平台注入），但不强制

#### 6.7.3 计划统一环境

建测试计划时可指定 **`environment_id`**，作为本计划内所有**通用用例**的执行环境。

```
Plan「每日冒烟」
├── environment_id = 测试环境
└── case_ids = [ 用例A(绑定包), 用例B(通用), 用例C(绑定包) ]

执行时：
  用例A → 用 A 自带环境
  用例B → 用计划统一环境（测试环境）
  用例C → 用 C 自带环境
```

计划环境**不覆盖**绑定包用例的自带环境，只为「没有环境的用例」兜底。

#### 6.7.4 环境解析规则（核心）

**一条规则：用例有环境用用例的，没有用计划的。**

```typescript
function resolveEnvironment(case, plan?, overrideEnvId?) {
  // 1. 用例自带环境（最高优先级）
  if (case.default_environment_id) return { source: 'case', id: case.default_environment_id };
  if (case.environment_snapshot_json) return { source: 'case_snapshot', snapshot: case.environment_snapshot_json };

  // 2. 计划统一环境（仅当用例无自带环境）
  if (plan?.environment_id) return { source: 'plan', id: plan.environment_id };

  // 3. 试跑 / MCP 显式传入
  if (overrideEnvId) return { source: 'override', id: overrideEnvId };

  // 4. 无法解析
  throw new Error('用例未绑定环境，且计划/请求未指定环境');
}
```

| 场景 | 用例类型 | 计划有 environment_id | 实际使用 |
|------|----------|----------------------|----------|
| 计划执行 | 绑定包 | 有 | **用例自带** |
| 计划执行 | 通用 | 有 | **用计划环境** |
| 计划执行 | 通用 | 无 | ❌ 执行前校验失败 |
| 单用例试跑 | 绑定包 | — | **用例自带** |
| 单用例试跑 | 通用 | — | 试跑弹窗**必选环境** |

#### 6.7.5 登录态解析

| 用例有 `case.auth.json` | 实际使用 |
|-------------------------|----------|
| 有 | **用用例 auth**（与绑定包一致） |
| 无 | 用 resolved_environment 的账号 **自动登录** |

计划环境不会改变绑定包用例已绑定的 Cookie；通用用例走计划环境的账号登录。

#### 6.7.6 对各生产面的指引

| 生产面 | 绑定包 | 通用用例 |
|--------|--------|----------|
| ① 录制 | 默认保存环境 + Cookie | — |
| ② 导入 | 三件套同导（spec + env + auth） | 仅导 script，标记 `portable` |
| ③ MCP | `import_case` 带完整 bundle | `import_case` 仅 script，`portability=portable` |
| 建计划 | 混合勾选两类用例 + 指定计划 `environment_id` | 计划环境服务于通用用例 |

#### 6.7.7 UI 提示

- 用例列表：标识「自带环境」/「通用」
- 建计划：选择通用用例时，若未填计划环境 → 阻止保存并提示
- 计划详情：展示「本计划环境：测试环境；其中 N 条通用用例将使用此环境，M 条绑定包使用各自环境」

#### 6.7.8 数据模型

```sql

default_environment_id INTEGER,              -- 有值 = 绑定包
environment_snapshot_json TEXT,                -- 有值 = 绑定包

```

```typescript
// caseHasOwnEnvironment → 用例环境；否则 → 计划环境
```

## 9. MCP Server 设计（生产面 ③）

独立包：`@uiauto/mcp-server`（或 monorepo 内 `mcp/`），通过 HTTP 调用 UIAuto 后端 REST API（带 API Token）。

### 9.1 定位

MCP 是平台的**对外编程接口**，与 Web UI 能力对等。外部调用方（大模型 Agent、IDE 插件、其他系统）可通过 MCP 完成：

| 领域 | 操作 |
|------|------|
| **用例** | 导入、查询、修改、删除、版本回滚、校验 |
| **环境** | 列表、创建、更新 |
| **计划** | 创建、更新、删除、查询 |
| **执行** | 单用例试跑、计划执行、取消 |
| **报告** | 读取试跑/计划执行结果与日志摘要 |

大模型生成用例是典型场景，但 MCP 不限于 LLM——任何有权限的集成方均可调用。

```
1. 遍历本地 spec 文件
2. import_case(name, script, tags)
3. create_plan(name, case_ids) → run_plan
```

## 10. 执行引擎统一

### 10.1 现状问题

当前存在两套路径：

- `executor.js`：clone Git 仓库 → 仓库内跑 Playwright
- `recordedRunner.js`：本地 workspace 跑单 spec

### 10.2 目标

**单一执行器 `CaseRunner`**：

```
输入: case_id(s) + environment_id + options(browsers, headed, ...)
  ↓
加载 case 脚本路径 + auth sidecar
  ↓
合并环境变量 / 写 auth.json / SwitchHosts
  ↓
在 data/cases/_workspace 下 npx playwright test <spec>
  ↓
收集 result_dir、截图、视频、日志
  ↓
写回 run_cases / case_runs
```

计划执行 = 按顺序对 `case_ids` 调用同一 runner（保持单队列并发模型）。

### 10.3 与现有能力对齐

| 能力 | 处理方式 |
|------|----------|
| 多浏览器 | 保留 `run_browsers_json` |
| WPS 账号登录 | 保留 `wpsAccountLogin` |
| Cookie / storageState | 用例 auth sidecar 或环境注入 |
| SwitchHosts | 保留 `switchhosts` 服务 |
| `SKIP_PLAYWRIGHT_DEPS` | 服务端部署策略不变 |

## 15. 总结

| 决策 | 结论 |
|------|------|
| Git 用例存储 | **完全移除**，不做兼容导入 |
| 核心资产 | **Case**：脚本 + 可选自带环境/登录；**Plan**：可选统一环境 |
| **用例模型** | **绑定包**（自带环境）与 **通用用例**（无环境）并存 |
| **环境解析** | **用例有环境 → 用用例的；无环境 → 用计划的** |
| **生产面（三条并列）** | **① 录制回放** · **② 手动导入** · **③ MCP 对外服务** |
| 控制面 | 用例库、环境、计划、执行、报告（Web UI 与 MCP 共用） |
| 执行 | **统一 CaseRunner**，单 workspace |
| 接口层 | REST（前端/录制器）+ MCP（外部集成），共用 Service 层 |

UIAuto 的定位从「Git 测试计划运行器」升级为「**自动化用例资产平台**」——三条生产面汇入同一控制面，在平台内完成承接、管理、调度与度量。
